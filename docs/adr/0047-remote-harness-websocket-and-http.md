# ADR 0047: Carry the harness protocol over bounded WebSocket and HTTP sessions

- Status: Accepted
- Date: 2026-09-25
- Baseline: 0006, 0008, 0022, 0037
- Scope: Remote `aim-harness/1` listeners and clients; the local unix, stdio and SSH transports keep their existing authority. The daemon's remote listener and gRPC adapter remain separate work.

## Context

The founding brief requires a standalone harness reachable over HTTP, gRPC or WebSocket (`docs/vision.md`, Requirements). ADR 0006 chooses JSON-RPC 2.0 over WebSocket text frames and HTTP request/response plus SSE, with gRPC scheduled later. The existing `Peer` provides request correlation, cancellation, ordered notification delivery, size limits and disconnect behavior for NDJSON byte streams (ADR 0037). The transport research recommends tokio-tungstenite 0.29 alongside the HTTP server stack and reqwest 0.13 for HTTP clients (`docs/research/infra.md`, infrastructure crates). Reusing `Peer` avoids a second set of RPC semantics.

An unauthenticated TCP listener would expose workspace file and process authority. The architecture requires network bearer authentication, TLS or a declared protected reverse proxy for non-loopback binds, Origin checks for browser-reachable endpoints, and request/body/concurrency limits (`docs/architecture.md` §12). The current local harness principal and unix peer-credential check do not establish network identity.

## Decision

- `aimx serve --ws ADDR` and `aimx serve --http ADDR` are mutually exclusive network listeners. A loopback bind may use cleartext but still requires a bearer; a non-loopback bind requires a direct rustls certificate/key pair or an explicit `--behind-proxy` declaration. Direct TLS and the proxy declaration describe transport protection; neither bypasses bearer checks.
- `aimx token create --scope read|write` returns a random bearer once. Only its SHA-256 digest, scope and expiry are stored in a private owner file. Concurrent issuers lock a stable private sibling file across the registry read/replace, so every displayed token remains registered. The `read` scope narrows the configured principal to read-only; `write` inherits only the server's configured authority. These two coarse token scopes become principal ceilings expressed through W20 `CallScope` at integration; per-call scopes can narrow them further.
- Network `initialize` must carry `AuthProof::Bearer`. HTTP requires the same bearer in every POST and SSE GET, and binds a random client-chosen `X-Aim-Session` identifier to the authenticated principal. The initialize proof must match the HTTP bearer. Token absence, mismatch and expiry fail closed; an attached peer is closed when its bearer expires. An Origin header must match an explicit allowlist; native clients without Origin are accepted. Tokens are never placed in URLs or logs.
- A WebSocket text message carries exactly one compact JSON-RPC message. Binary frames, embedded line breaks and oversized messages are refused. The WebSocket adapter bridges into the existing NDJSON `Peer`, retaining its cancellation, ordered notifications and backpressure; tungstenite frame and message limits are applied before payload allocation.
- HTTP `POST /rpc` carries one JSON-RPC request or notification and returns the matching response or an empty notification acknowledgment. `GET /events` is one bounded SSE notification stream for that HTTP session. Each POST carries an increasing `X-Aim-Sequence` so requests and later `$/cancel` notifications are admitted to the peer in client order even when HTTP connections race. The bridge releases that ordering gate as soon as a frame enters the peer, before waiting for its response. It also correlates concurrent POSTs by request ID and preserves the per-peer `initialize` state. Bodies, pending calls, connections and HTTP sessions are bounded; a timed-out header or body and an idle socket release their connection slot. An admitted long `exec.read` or `exec.wait` may await its result without an arbitrary 30-second transport deadline, while the in-flight limit still bounds resource use. Dropping the last SSE stream detaches the peer; a periodic reaper closes abandoned HTTP sessions. A slow SSE subscriber receives a lag signal and must reconcile state using `exec.read {after_seq}`.
- `HarnessClient::connect_ws` and `connect_http` establish an authenticated remote peer and open a workspace root. Their resume variants send `initialize {resume}` on a new connection; consumers reconcile process output with `exec.read`. Cleartext client URLs are permitted only for numeric loopback addresses; HTTP proxies and redirects cannot carry local cleartext bearers onward. Workspace-location configuration is deferred rather than adding a second persisted location format in this change.
- HTTP POST responses and SSE events use separate connections. The adapter orders a response before making later notifications available to SSE, but the network does not guarantee cross-connection arrival order. Clients use sequence numbers and `exec.read` for authoritative stream reconciliation.

## Consequences

The harness can operate remotely without a second protocol schema. WS is the continuous full-duplex transport; HTTP is a compatible request/stream option with extra session and reconnection state. HTTP notification delivery is a hint, while process output remains recoverable through the existing ring-buffer read and resume token. Operators must protect proxy-to-aimx links if they use `--behind-proxy`, provision token lifetimes, and maintain the Origin allowlist for browser clients. The token registry adds a private owner file under `~/.aim`; it is separate from Codex authentication.

## Verification

Transport conformance tests in `crates/aim-rpc/tests/{ws,http}.rs` cover frame mapping, refusal, cancellation, ordering, long waits, limits and notification delivery. `crates/aimx/src/server/{network,token}.rs` tests bearer refusal and expiry, concurrent token issuance, HTTP session reclamation, Origin, TLS bind policy, and WebSocket resume with `exec.read` recovery. `crates/aim/src/harness.rs` live tests connect and resume through both remote client constructors. On the integrated branch, `mise run check` passed; the localhost TLS WebSocket smoke sampled 25 sequential `tools.list` calls at 518.333 µs/call versus 186.411 µs/call for unix in the same process. Those numbers are a smoke comparison, not a benchmark distribution. The policy decision for listener safety is small pure logic that may move to `aim-kernel` after the token and proxy inputs settle.
